## 二、方案哪里说错了（三处，都影响排期）

### 2.1 §1.3 的因果链不成立 —— 但它猜对了"症状"

方案说：

> 选举收敛失败 → ALOHA 抢发 → 帧跨 cycle → TDOA 相减 ≈ 0 → 解算质心

**代码里没有运行期 Root 选举。** `fusion_anchor.c` 的 `STATE_ELECTING` 在手动模式下被直接绕过
（注释原文 "In manual mode, this state is bypassed"），Root 由上位机指定；
`STATE_SCAN` 只在 `FORCE_RESET` 时进入。方案里"选举收敛失败"这一环**没有对应的代码路径**。

而且 **ALOHA 帧进不了主解算**：标签在装配 TDOA 时显式排除 `slot == 255` 的锚点
（`fusion_tag.c` 的 raw-RX 兜底分支只收 `slot == 255` 的锚点，
而主路径 `tag_solve()` 只收 `slot != 255` 的），所以"抢发的帧混进解算"这条路是堵死的。

**但是**：方案猜的**结果**（"TDOA 相减 ≈ 0"）恰恰是对的，而且我在宿主端复现了它 ——
只是它发生在**测量层**，不在选举层。见 §三。

> **对排期的影响**：M3"Anchor 去 Root 化"要解决的是**架构问题**（单点失效、跨区混解算），
> 不是"质心"的根因。把"输出质心"的修复押在 M3 上会押错。

### 2.2 M2「只改协议头，三端不改逻辑」做不到

方案提议复用 `DL_TS_LEVEL_IDX`（原 `cs_level`）当 `zone_id`、并删掉 `parent_eui64`（8 字节）。

- **LEVEL 字节不能直接当 zone_id**：它现在的语义是 `cs_level`（时钟同步等级），
  锚点用它来挑参考锚点/父站。改成 zone_id 就等于改语义 → **三端都要改**，
  "只加字段不改逻辑"不成立。要么保留 cs_level 另开字段，要么明确接受语义变更并同步改三端。
- **删 `parent_eui64` 会移动 8 个字节**：信标帧 67 → 59 字节，
  `DL_TIMESYNC_MIN_LEN` 必须同步从 **63 改成 55**（它现在就是下限检查，帧短于它会被丢），
  标签/基站/网关**三处**的长度下限都要跟着改。

> **建议**：M2 改成"**只加字段，不删字段**"：`zone_id` 用新偏移追加在 `parent_eui64` 之后，
> 帧长 67 → 69（尾部仍有 `0xCC 0xDD` 吸收 DW3210 末 2 字节损坏）。
> `parent_eui64` 现在**写了从不读**（`fusion_anchor.c:1220` 写入，全工程无读点），
> 留着它没有代价，删它却要动三端的长度判据。**删字段放到最后一个里程碑**，
> 那时协议已经有版本号兜底。

### 2.3 §8.1 的文档清理会误删记录

方案 §8.1 提议删除 `docs/代码审查报告.md` 和 `docs/UWB_TDOA3_Optimization_Plan.md`，
并列出"docs 只保留 5 份"的目标清单 —— 清单里那份
`UWB_TDOA_技术路线与开发分工.md` **当时还不存在**（现已有）。

- `docs/代码审查报告.md` 是 **16 项未修复 P0/P1 的唯一台账**（含位置、后果、优先级）。
  删掉它，这些待办就只剩"脑子里记得"。
- `UWB_TDOA3_Optimization_Plan.md` 按架构文档 §六 的约定是**历史备查**。

> **结论**：**这两份不删**。清理只针对**代码**（`auto_anchor.h` 等），文档层维持"新增不删、

## 三、复核出来的真东西：「输出恒等于质心」到底怎么发生的

方案 §2.5 的原则是"**宁可不出，也不输出质心**"。我把它当成一条可实现的规格去查，
结论分两半：

### 3.1 求解器不是元凶（已用宿主端实测排除）

`shared/downlink/tdoa_solver.c` 是纯计算（只 include `<math.h>` / `shared_defines.h` /
`downlink_protocol.h`，唯一 extern 是 `test_run_info`），
所以它**可以在开发机上编译并运行**。本轮写了 `test/solver_host_test.c`，
实测 13 个用例：

| 用例 | 旧行为 | 说明 |
|---|---|---|
| 4 锚正方形，标签在内 | 解出，误差 **3.8 cm** | 求解器核心是对的 |
| 4 锚正方形，标签**恰在质心** | 解出，误差 3.2 cm | **合法解** —— 这条禁止"质心禁令" |
| 3 锚（恰好定解） | 解出，误差 5.8 cm | |
| 6 锚环形 | 解出，误差 5.0 cm | |
| 4 锚共线，标签**离线** | 解出，误差 4.4 cm | **走廊部署是合法的** |
| 4 锚共线，标签**在线** | 解出但**偏 65 cm，残差只有 2.8 cm** | ← 自信的错误答案 |
| 4 锚全重合 | 解出，**残差 1e9 cm** | ← 数值已经疯了还是发了出去 |
| 3 锚重合 + 1 锚 | 解出，**偏 590 cm，残差 2.3 cm** | ← 自信的错误答案 |
| **2 锚** | 解出，**残差无穷大** | ← 欠定 |
| 4 锚 + **全零 TDOA** | **解出 = 质心**，残差 12.6 cm | ← **"质心"现象本身** |
| 4 锚 + 垃圾 TDOA | 解出，偏 189 cm，残差 34 cm | 残差指标能看见这类 |
| 槽误差 10 cm/槽 | 偏 14 cm | |
| 槽误差 375 cm/槽（20 ppm） | **偏 7.9 m**，残差 229 cm | 质量分能看见这类 |

**结论**：求解器的几何与迭代是对的（良好几何 3~6 cm，受 DTU 量化限制），
但它有**四个能"自信地输出错误答案"的洞**，而**质心现象只在"全零 TDOA"这一种输入下出现**。

### 3.2 关键限制：质心禁令在求解器里**不可能**实现

"全零 TDOA"这一行和"标签恰在质心"那一行，**输入完全相同**：
4 个正方形锚点、TDOA 全 0。两种情况下求解器的输出必然相同（都是质心，残差都小）。

> 所以"检测出质心就拒绝"这条规则会**误杀合法解**；
> "禁止输出质心"这条规则**在求解器内部无法实现** —— 输入相同，输出必须相同。
>
> **判别只能发生在知道测量来路的标签层**：标签必须能判断"这组 TDOA 是不是我可信地配对出来的"，
> 而不是"解出来的点像不像质心"。
> 这是本轮给方案 §5.3 的一条**实施修正**：质心防护分两处 ——
> 求解器负责"几何撑不住就不出数"（本轮已做），
> 标签层负责"配对不可信就不出数"（**M4 的硬性验收项，本轮未做**）。

> **旁证**：本文件 §五 的「per-anchor 单程映射给不出绝对 TDOA」一行早就记下了同一条机制 ——
> "每帧各自刷新参考时 TDOA ≈ 0 ⇒ 精确复现「输出恒等于质心」"，
> 并写明"绝对 TDOA 只能来自①公共时基②锚↔锚往返测量③有线公共参考，**这是设计约束，任何改动不得违反**"。
> 本轮的工作是把它**从静态推理变成可复现的数值**，并划清了求解器与测量层各自的责任边界。
> 顺带也说明：**方案决策 1（网关下发 `zone_time_base`）正是在落实①公共时基**，方向被既有分析印证。
>
> **别读混了**：标签当前的 TDOA 走的是**槽补偿（栅格时基）**，**不是** `clock_sync` 的 per-anchor 映射
> —— 那一行记的是同一类机制（参考对把传播时延吸收掉 ⇒ TDOA ≈ 0）的静态推理。
> 标签当前路径的主要风险在**槽补偿的速率精度**（§3.3 的 7.9 m），不在映射。

### 3.3 顺带量化了方案最担心的东西：槽补偿误差

标签的槽补偿是 `toa = rx_local − slot × 6.25 ms`，其中 6.25 ms 要乘**标签对 Root 的速率估计**。
速率估计差 d ppm 时，**一个槽就是 6.25 ms × d ppm 的路径误差**，
而 TDOA 误差**随槽号线性增长**。实测（正方形 4 锚，锚点按槽号排列）：

- 每槽 **10 cm** 路径误差 → 位置偏 **14 cm**（放大约 1.4 倍）
- 每槽 **375 cm** 路径误差（= 20 ppm 下一个槽）→ 位置偏 **7.9 m**，残差 229 cm

20 ppm 是标签**单周期（50 ms）速率估计**的量级。
所以 M4 之前，**标签侧速率估计的精度就是定位精度的主项**；
方案把"槽补偿精度"列进 M1/M4 的方向是对的，但**没有给出这个数字** —— 这里是。

## 四、需你拍板的 5 件事：我的结论

### 决策 1：区内公共时间轴 —— **用网关 `zone_time_base`（同意方案）**

理由：迭代平均需要区内每个锚点两两同步，锚点一多就是 N² 的耦合，
而且**收敛时间随规模变长**，正好和"要快速出位置"相反。
网关单点下发时基是 O(1) 的，代价是网关成为单点 —— 但网关本来就在链路上，
它现在还兼着组网和 OTA，下发一次时基不增加新的单点。

**但要补一条**：网关下发的时基必须**带自己的新鲜度**（网关自己的时间戳 + 轮次），
否则锚点无法判断时基是不是上一轮的。这和"时钟同步"是两件事，
方案里 `zone_time_base` 只写了"一个时间基准"，没写新鲜度传递 —— **要补**。

### 决策 2：一期是否允许跨区复用信标 —— **不允许（同意方案）**

理由：单信道下，两个区复用同一个槽就是**槽冲突**，不是"复用"。
真要跨区复用，得先做信道切换或跳频，这不在一期范围内。
跨区坐标融合（决策 4）可以先做 —— 它只需要两区各自的解和各自的坐标，**不需要跨区信标**。

### 决策 3：单向链路锚是否直接剔除 —— **剔除，但先区分"没听到"和"听到了但对不上"**

方案的"直接剔除"是对的（单向链路给不出 TDOA，留着只会污染方程）。
但要区分两种情况：
- **从来没收到过这个锚点的信标** → 剔除；
- **收到了，但周期/槽位对不上**（`cycle_id` 不匹配）→ 这不是链路问题，是**配对问题**，
  直接剔除会把"仅仅是这一轮没配上"的锚点踢出解算，让解算在网络抖动时频繁掉锚。

**建议**：剔除的理由要分开计数（`n_no_beacon` / `n_cycle_mismatch`），
只把"从来没收到过"的剔除；"对不上"的先留一轮观察，连续 N 轮对不上才剔除。

### 决策 4：16 基站 —— **拆 2 区 × 8 + 跨区坐标融合（同意方案）**

理由：`DL_MAX_ANCHORS 8` / `ANCHOR_MAX_SLOTS 8` / `NET_MAX_SLOTS 8` 三处都是 8，
硬扩到 16 要动协议帧长（slot 表 8×u16）、slot 周期（8 槽 = 50 ms，16 槽 = 100 ms）
和 RAM。**2 区 × 8 的好处是 16 基站时单区周期不变**，20 Hz 的解算率也不掉。

补充一条方案没提的：**跨区坐标融合必须等两区各自的解都可信**。
两区各 8 锚时每区单独定位是可以的，但融合的前提是**两区之间有共同的坐标基准**
（同一套网关下发的坐标系）。如果两个区的坐标系各自独立（各自的 zone 原点），
那"融合"就是把两个坐标系的数相加 —— **必须先统一原点**。
方案 §4 的区模型里，`zone_time_base` 讲了，但**区的坐标原点没讲** —— **要补**。

### 决策 5：16 标签同时在线是否降信标下行频率 —— **降，但只降信标，不动定位帧**

算一下：16 标签 × 20 Hz = 320 帧/s 是**上行**（标签→网关）。
下行是**信标**（锚点→标签），帧率由 TDMA 栅格决定：8 锚 × 20 Hz = 160 帧/s，
每帧 67 字节 ≈ 268 bit → 160 × 268 = **42.9 kbit/s**。DW3000 在 6.8 Mbps 下单信道绰绰有余。

**所以决策 5 的前提需要核对**：如果瓶颈是**空口时间**，
8 槽 × 6.25 ms = 50 ms 的超周期里，8 个信标各占 6.25 ms —— 一帧 67 字节在 6.8 Mbps 下
只要 **0.4 ms**，占空比只有 6%。**空口不是瓶颈**。

真正的瓶颈是**标签的上行**：16 标签 × 20 Hz × 24 字节 = 7.7 kB/s，
以及网关串口（921600 baud ≈ 92 kB/s）—— 占 8%。也够。

**结论**：**一期不用降频**。如果 16 标签上线后确实压住了网关串口，
先降的是**上报帧率**（20 Hz → 10 Hz）或**只上报位置变化**，
不是信标 —— 降信标会直接降定位精度和标签的解算率。
**但这个结论依赖"单信道 6.8 Mbps"这个前提，上机前要用 `+POS` 的实际速率核对一次。**

## 五、本轮已落地的代码改动

方案 §5.3 的"病态检测 + 退化保护"被抽出来**提前做了**，理由是：
它是**唯一一个可以脱离硬件验证**的部分（求解器是纯计算），
而且它与 M3/M4 的重写**正交**（只改 `tdoa_solver.c`，不碰协议、不碰架构）。

### 改动 1：`shared/downlink/tdoa_solver.c` —— 三道闸门

见 `docs/系统架构与算法说明.md` §3.5 的表格。摘要：

1. `n < 3` → `-2`（原来 `n < 2`，2 锚会返回残差无穷大的位置）；
2. **不同位置的锚点数** `< 3` → `-1`（重合锚点是"戴帽子的 2 锚系统"）；
3. 末次更新用了**奇异**正规方程 → `-1`（原来加 1e-3 岭正则后继续，步长消失、解停在种子=质心）；
4. 水平正规方程**条件数份额** `< 0.010` → `-1`；
5. 残差非有限或**超过锚点最大间距** → `-1`。

### 改动 2：`test/solver_host_test.c` —— 本项目第一个可执行测试

纯 C，无依赖，`gcc` 直接跑：


## 六、给 M3/M4 的验收项（建议直接写进里程碑）

1. **M4 必须包含"质心防护"**（本轮 §3.2 的结论）：标签层要能判别"这组 TDOA 配对不可信"，
   而不是靠解出来的点像不像质心。验收：人为制造一次槽错配，
   标签**不得**输出位置（现在会输出）。
2. **M1 要给出槽补偿的误差预算**：现在只有一个数（20 ppm → 每槽 375 cm → 位置 7.9 m），
   标签侧速率估计要收敛到多少 ppm 才够用？
3. **M2 改成"只加不删"**（见 §2.2），删字段放最后一个里程碑。
4. **M4 的区模型要补"区的坐标原点"**（见决策 4）。
5. **M1 的 `zone_time_base` 要补新鲜度传递**（见决策 1）。
